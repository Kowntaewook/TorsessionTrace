# Separate-host v3 onion pilot: client RAM and service request truth

**Validation status:** three selected client captures have been cross-checked against their completed independent service-run artifact. A fourth Windows clicked client passed whole-RAM validation and recorded two target requests through the service's `/status` endpoint. The fourth service runner is still awaiting a failed `/finish` notification; final cross-check of its service-side artifact is pending. Accordingly, the four-cell pilot is not yet called fully cross-verified.

The [locked protocol and amendments](remote-host-protocol.md) moved the ephemeral v3 onion service to a separate GitHub-hosted Ubuntu runner. Client jobs on separate Linux and Windows runners started independent Tor daemons, loaded the onion landing page in Tor Browser 16.0, and captured whole RAM with AVML or WinPmem while the browser was alive. A distinct randomized target path existed for each OS × condition. The service counted requests to that path separately from readiness, landing, status, and completion traffic. The one selected image per cell is an engineering pilot, not a detection-rate sample.

For the first three selected clients, the independent [service record](../research-results/2026-11-03-remote/service-attempt1.json) agrees on target-request counts, service run ID, and hashed onion hostname. The fourth client record is [here](../research-results/2026-11-03-remote/windows-clicked-1.json); its service-side record must still be recovered and compared. The client shows two browser click attempts, final browser URL equal to the target, all nine recorded browser PIDs present in RAM `pslist`, a 11.00 GiB whole-RAM image hash, 14 adapter target hits, and 22 generic target-blind YARA target hits. Its `/finish` notification failed after validation. This notification is for runner shutdown; it is not the target request or the memory scan. The service eventually writes counters on timeout, even if the job concludes with a technical failure.

The four service dispatches produced **16 actual client job attempts**: nine client jobs completed analysis and seven failed. The four selected client images are the earliest analyzable capture for each cell; five later successful jobs are listed but not added to the planned one-per-cell denominator. The seven failures comprise four pre-repair validator argument errors after capture, one Windows landing-page failure, one Linux RAM image whose browser PIDs were absent from `pslist`, and one Windows click that yielded no target request before capture. The [attempt manifest](../research-results/2026-11-03-remote/manifest.json) links every failed or selected job. Earlier service records, including the [pre-repair service](../research-results/2026-11-03-remote/service-prerepair.json) and [third dispatch](../research-results/2026-11-03-remote/service-attempt2.json), retain service-side counters even where clients could not yield an analyzable image.

The [first service run](https://github.com/Kowntaewook/TorsessionTrace/actions/runs/41550300161), [second](https://github.com/Kowntaewook/TorsessionTrace/actions/runs/41550538294), [third](https://github.com/Kowntaewook/TorsessionTrace/actions/runs/41551406883), and [fourth](https://github.com/Kowntaewook/TorsessionTrace/actions/runs/41552523820), together with their dispatched [first](https://github.com/Kowntaewook/TorsessionTrace/actions/runs/41550362682), [second](https://github.com/Kowntaewook/TorsessionTrace/actions/runs/41550598132), [third](https://github.com/Kowntaewook/TorsessionTrace/actions/runs/41551827714), and [fourth](https://github.com/Kowntaewook/TorsessionTrace/actions/runs/41552571456) client runs, preserve acquisition and failure logs. Raw RAM and onion private keys were not uploaded. The records release SHA-256 hashes and counts, not URLs or memory strings. This setup confirms separate hosted machines at the workflow level; no Tor circuit packet capture or independently redistributable RAM corpus was produced.
