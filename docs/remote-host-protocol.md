# Remote-host v3 onion pilot: locked protocol

**Status before results:** service, client, and validation source plus this protocol are committed before the first remote-host capture. This pilot isolates the onion service from the browser by running them on **different GitHub-hosted machines**. It does not claim packet-level observation of Tor circuit paths.

**Technical amendment after first attempts:** the client validator omitted the optional `baseline_yara` argument and was repaired before a replacement run. Tor Browser landing navigation can retry up to three times, with the count recorded, after one Windows client could reach the service with curl but did not load the landing page on its first browser attempt. The scenario and target-blind rule are unchanged.

A Linux service job starts an ephemeral v3 onion service and a local HTTP server. After Tor bootstrap, it dispatches a separate workflow using `workflow_dispatch` and stays alive while client jobs run. Two independent Linux jobs and two independent Windows jobs each start their own Tor client daemon, load the remote onion landing page in Tor Browser 16.0, then capture whole RAM with AVML or WinPmem. Within each OS, one job leaves the target link unclicked and one clicks it. The service provides a distinct randomized target path for each OS × scenario and counts `/target` requests separately from `/ready` and `/landing`. The client queries the service counter after capture; the service uploads its own counter artifact, allowing cross-run comparison.

The primary unit is one client whole-RAM image. The four cells each have **one planned analyzable image** and are a connectivity and measurement pilot, not a detection-rate study. Failed attempts remain visible in workflow logs and must be replaced before reporting four analyzable images. The service and client workflow run IDs, image hash, onion hostname hash, browser binary hash, recorded and RAM-observed process PIDs, request counters, target hit counts, generic target-blind YARA counts, and timings are reported. Raw RAM and extracted strings are deleted or withheld. The ephemeral hostname and random token are transmitted through private workflow inputs so client runners can connect; they are not intended as public corpus identifiers.

Protocol acceptance depends on service bootstrap, SOCKS5h readiness, browser landing, stable browser PIDs in RAM, client Tor PID in RAM, and target-path request count matching `link_only` (zero) or `clicked` (positive). Detection is an outcome and cannot determine analyzability. The same target-blind YARA expression from the [extended study](extended-study-protocol.md) scans the same PIDs. Service-side and client-side counters must agree before interpreting a capture. This design tests a genuinely separate service host but remains constrained to hosted runners, headless browser use, one browser version, and a short capture interval.
